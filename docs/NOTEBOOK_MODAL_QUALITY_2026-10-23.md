# ノート画像の高解像度取得（2026-10-23）

## 変更内容

- 一覧用は既存の幅640pxプレビューと圧縮・更新間隔を維持する。
- 教師が開いている生徒のモーダルだけ、カメラ映像から台形補正を別に実行する。同じ四隅・用紙比率を使用する。
- 撮影は3840×2160を希望値として要求し、1080p・中間解像度のカメラでもその機種で取得可能な映像を使用する。解像度を必須値にはしない。対応ブラウザーでは `resizeMode: { exact: "none" }` を指定し、ブラウザーによる撮影元の拡大を避ける。
- 高解像度での起動が制約不一致・機器読出しエラーで失敗した場合は、1080pを希望値として1回再試行する。権限拒否などは再試行せず、従来の起動失敗表示へ進む。
- 画像の長辺上限を2560pxから3840pxへ変更。実際の映像と指定した四隅の画素座標から四辺の長さを求め、反対側の辺のうち画素数が多い側の細部を用紙比率に合わせて残す。出力はカメラ映像の長辺も超えない。ノートが映像の一部しか占めない場合は、その範囲に応じた画像サイズとなる。JPEG品質は0.92を維持する。元の補正結果は通常640×905、モーダル送信時のJPEG品質は0.6だった。
- 高解像度フレームはRealtime用の約120KBへの再圧縮を通さず、非公開Storageへ保存し、`student-screen-update` にパスと更新識別子を載せる。教師は認証付きで取得して描画する。Socket.IO利用時は同じ高解像度画像を個別モーダルへ直接送信する。
- 保存先は `students/{studentId}/realtime/{classId}-notebook.jpg`。認証中の生徒から所有者を解決する。最新1枚を上書きするため、更新ごとにファイルが蓄積しない。最終画像は生徒の領域内に残り、生徒・クラス削除時の既存クリーンアップ対象となる。
- 保存は `cacheControl: "0"`、取得は更新ごとの `cacheNonce` と `cache: "no-store"`。既存のRLSを使用し、DB・権限の変更はない。
- 通常は既存の監視ループで約3秒おきに更新する。先生が閉じる・別の生徒へ切り替える・ページから離れると停止要求を送る。作成・保存・取得・デコード中に対象が変われば古い応答を反映しない。
- ズーム・パン・教師の注釈は、同じ大きさのノート画像の定期更新で維持する。接続中の生徒を旧ノート一覧から開く場合も共通の監視モーダルへ接続する。

高画質化に伴い、モーダルを開いている生徒の画像転送量・補正処理負荷は増える。カメラのピント、照明、元映像にない細部はこの変更では復元されない。

## 検証

- `npm.cmd test`：新規のモーダル画質テストを含む全テスト成功。
- `npm.cmd run test:browser:notebook`：Edge、仮想1920×1080・2560×1440・3840×2160カメラ、ローカルのStorage/Realtime代替処理で全ケース成功。
- 同じ四隅でのモーダル画像は、1080pで1344×1901px、中間解像度で1793×2535px、4Kで2689×3804px。4Kでは以前の2560px上限を超える細部を保持し、一覧用は全ケース640pxだった。出力寸法は指定範囲で変わるため、この寸法が常に使われるわけではない。
- ブラウザーで入力サイズと、四隅に応じた補正画像のデコード・Canvas描画、旧120KB上限を超える画像の受渡し、更新後のズーム・注釈保持、停止・再開を確認。解像度選択の失敗時の再試行はユニットテストで確認。
- 作成・保存・取得・デコード中の閉じる／切替、古い画像の到着順序、通信失敗後の復帰をローカルの実ハンドラー検証で確認。
- 320/375/683/768/1024/1366pxで既存のカメラ・補正後レイアウトを確認。横にはみ出しなし、ページ例外なし。
- ブラウザー結果：`output/playwright/notebook-refresh/results.json`（1080p・既存レイアウト回帰）、`output/playwright/notebook-refresh/camera-resolutions.json`（3解像度）。画像：同フォルダーの `high-resolution-modal-1920.png`・`high-resolution-modal-2560.png`・`high-resolution-modal-3840.png`。
- 接続先のStorageポリシーを読取専用SQLで確認し、生徒本人の保存と担当教師の取得が既存権限内で可能なことを確認。認証付きの実際のアップロード／ダウンロード試験は未実施。

## 公開前後の確認

本変更はローカルでの実装。公開反映と、実機・認証済みSupabaseでの画質改善は未確認。

1. 別端末の教師1人と生徒2人で参加。生徒は細かい手書き文字のあるノートを撮影・台形補正する。
2. 一覧だけの状態で高解像度ノート画像のStorage通信が発生しないことを確認する。
3. 生徒Aのモーダルを開き、Aだけ高解像度画像が保存・取得され、文字を拡大して読めることを確認する。
4. 注釈とズームを設定し、20秒以上待って更新後も維持されることを確認する。
5. 生徒Bへ切替。Aの高解像度送信停止、Bの取得開始、遅れて届くA画像の非表示を確認する。
6. 閉じた後は一覧・カメラが更新し続け、高解像度ノート画像の通信は停止することを確認する。教師ページからの離脱も同様に確認する。
7. 1080p・中間解像度・4Kの実機カメラを接続し、コンソールの `Notebook camera started` の実取得解像度を確認する。Chromebook/iPadで補正中の操作応答と通信量を確認し、ピントや照明の影響を送信時の圧縮と区別する。4K取得可否はカメラ・USB接続・端末・ブラウザーの組合せで確認する。

Storageの取得・上書き・キャッシュ回避は [Supabase upload](https://supabase.com/docs/reference/javascript/storage-from-upload)、[download](https://supabase.com/docs/reference/javascript/storage-from-download)、[Smart CDN](https://supabase.com/docs/guides/storage/cdn/smart-cdn) を参照。

カメラの希望値指定は [getUserMedia](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia)、実取得設定は [getSettings](https://developer.mozilla.org/en-US/docs/Web/API/MediaStreamTrack/getSettings) を参照。仮想映像のテストは実機カメラの解像度交渉を実証するものではない。
