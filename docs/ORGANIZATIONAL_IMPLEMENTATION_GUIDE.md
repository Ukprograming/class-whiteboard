# Class Whiteboardを組織として開発・実装するために必要なもの

## 1. この資料の目的

Class Whiteboardは、教員と生徒が授業中にホワイトボード、画面、チャット、ノート画像などを共有し、教員が学習状況を確認して助言できるWebアプリです。

これまでは個人による非公式な開発・試行でしたが、今後、組織の正式な取組として開発・実装する場合、必要になるのはアプリの改良だけではありません。利用者の情報を誰がどのように守るか、障害や事故に誰が対応するか、将来も保守を続けられるかまで、組織として決める必要があります。

この資料では、非エンジニアにも判断しやすいように、必要なものと、その理由を整理します。

> **重要**
>
> - この資料は、2026年8月26日時点のソースコードと既存資料を確認して作成した、検討開始用の資料です。
> - 法令の適用や必要な手続は、組織が公的機関か民間組織か、利用者の年齢、扱う情報、利用地域などによって異なります。最終判断は、組織の個人情報保護・法務・情報セキュリティ担当者と行う必要があります。
> - 現在の実装に一定のアクセス制御はありますが、この確認は第三者による脆弱性診断や本番運用の安全性を保証するものではありません。

---

## 2. 結論：まず必要なもの

最優先で必要なのは、次の5点です。

1. **組織としての責任者と意思決定の仕組み**
   - 誰がサービスの提供責任、個人情報の管理責任、技術判断、事故対応を担うかを明確にします。
   - 個人開発者一人だけが全てを知り、全てに対応する状態を解消するために必要です。

2. **組織が管理するシステム基盤**
   - 現在のSupabase個人契約をそのまま本番利用するのではなく、組織名義のクラウド環境、組織の既存サーバー、又は正式に採用したサービスへ移します。
   - 契約、支払、管理権限、障害対応、データの所在を組織が把握し、担当者が交代しても運用できるようにするためです。

3. **運用ルールと個人情報取扱ルール**
   - 収集する情報、利用目的、閲覧できる人、保存期間、削除方法、バックアップ、事故時の連絡方法などを定めます。
   - 技術的に保存できることと、組織として保存してよいことは別だからです。

4. **専門家による技術・セキュリティ支援**
   - システム設計、セキュリティ、クラウド運用、データ移行、テストを担当又は支援できる人が必要です。
   - 本アプリは、認証、個人別のアクセス制御、画像保存、リアルタイム通信など、専門的な確認を要する機能を含むためです。

5. **段階的な試験と正式運用への移行手順**
   - 架空データによる試験、組織内ステージング、限定された実証、正式運用の順に進めます。
   - 実在する生徒の情報を使いながら設計やルールを考えることを避け、問題が起きた際の影響を小さくするためです。

サーバーだけを用意しても、組織として安全かつ継続的に利用できる状態にはなりません。**「基盤」「ルール」「人」「検証」「継続予算」を一体で準備すること**が必要です。

## 3. 現在のアプリはどのような構成か

現在のステージング構成では、役割が次のように分かれています。

```text
教員・生徒の端末
       │
       ▼
GitHub Pages
画面や操作部分を配信する
       │
       ▼
Supabase
├─ Auth：教員・生徒のログインと本人確認
├─ Database：クラス、生徒、保存ファイルの台帳
├─ Storage：ボードデータや画像を保管する非公開の書庫
├─ Realtime：在席確認、チャット、画面確認、共同編集の通信
└─ Edge Functions：生徒作成・削除など、強い権限が必要な管理処理
```

つまり、現在のSupabaseは単なる保存場所ではなく、**受付、名簿、書庫、授業中の連絡回線、管理事務**をまとめて担っています。

別のサービスや組織内サーバーへ移す場合は、これら全ての代替手段が必要です。サーバーを1台用意するだけでは、ログイン、権限管理、ファイル保存、リアルタイム通信、バックアップ、監視などは自動的には整いません。

また、リポジトリにはExpress／Socket.IOによる旧ローカル互換機能も残っていますが、現在の資料ではローカル確認用とされており、生徒ごとの本番向け認証を備えた代替基盤ではありません。そのまま正式運用用サーバーとして採用する前提にはできません。

| 開発・変更ルール | ソースコード管理、レビュー、テスト、承認、リリース、緊急修正 | 変更によって授業中の停止や情報漏えいを起こさないため | 開発標準、リリース手順 |
| 技術支援体制 | 設計、バックエンド、セキュリティ、インフラ、テストの支援 | 現在の機能には複数分野の専門知識が必要なため | 支援契約又は担当者表 |
| セキュリティ対策 | 多要素認証、最小権限、秘密情報管理、診断、更新、監視 | 画面上でボタンを隠すだけではデータへの不正アクセスを防げないため | セキュリティ要件、診断報告 |
| 利用者向けルール | 利用目的、禁止事項、撮影・共有の注意、問い合わせ、同意又は周知 | 利用者が何を記録・共有されるかを理解できるようにするため | 利用規約、プライバシー説明 |
| 試験環境 | 開発・検証・本番の分離、架空データ、受入試験 | 開発中の誤操作が実データや授業へ影響しないようにするため | テスト計画、受入記録 |
| 利用支援 | マニュアル、研修、問い合わせ窓口、障害時の代替授業手段 | システムがあっても、現場が安全に使えなければ定着しないため | 操作手順、FAQ、研修資料 |
| 契約・知的財産の整理 | コードの権利、素材・ライブラリのライセンス、委託契約 | 個人制作物を組織が公に提供・改修できる根拠が必要なため | 権利確認書、ライセンス一覧 |
| 継続予算 | 利用料、人件費、診断、保守、端末試験、研修、予備費 | 初期開発費だけではサービスを継続できないため | 複数年度の費用見通し |

## 5. 「サーバー」として必要な機能

### 5.1 サーバーは「機械1台」ではなく、複数の機能の集合

正式運用では、少なくとも次の機能が必要です。

| 機能 | このアプリでの役割 | 欠けた場合に起きること |
| --- | --- | --- |
| Web配信 | 教員・生徒の画面を端末へ届ける | アプリを開けない、更新を配布できない |
| 認証 | 教員・生徒が誰かを確認する | 他人になりすました利用を防げない |
| 認可・権限管理 | 所属クラス、教員・生徒、データ所有者に応じて操作を制限する | 別クラスや別の生徒のデータが見えるおそれがある |
| データベース | クラス、生徒、ファイル名、所有者などを管理する | 誰のデータか、誰が閲覧できるかを管理できない |
| ファイル保存 | ボード、挿入画像、ノート画像等を保存する | 作成物を保存・再利用できない |
| リアルタイム通信 | 在席、チャット、画面確認、共同編集を中継する | 授業中の双方向性が失われる |
| 管理用サーバー処理 | 生徒作成・削除、パスワード再設定、一斉配布等を安全に処理する | 強い権限をブラウザへ置く危険が生じる |
| ログ・監視 | エラー、異常アクセス、容量、応答時間を確認する | 問題に気付けず、原因調査も困難になる |
| バックアップ・復旧 | 誤削除や障害からデータを戻す | データを失ったときに復旧できない |
| DNS・TLS・通信防御 | 正式URL、通信暗号化、攻撃や過負荷への基本対策 | 利用者が正しい接続先を確認できず、通信や可用性のリスクが高まる |

### 5.2 基盤の選択肢

| 選択肢 | 長所 | 注意点 | 適する状況 |
| --- | --- | --- | --- |
| 組織が既に採用している共通基盤 | 契約、監視、ID管理、問い合わせ体制を共用しやすい | リアルタイム通信や画像保存が使えるか、機能制約の確認が必要 | 組織に成熟した情報基盤がある場合 |
| 組織名義のマネージドクラウド／BaaS | 初期構築と日常保守の負担を抑えやすい | 事業者審査、保存地域、契約、料金、障害、サービス変更への備えが必要 | 小規模実証から段階的に始める場合 |
| 組織が契約する一般クラウドに個別構築 | 要件に合わせやすく、構成の選択肢が広い | 設計・構築・監視・セキュリティの専門体制が必要 | 組織内にクラウド運用能力がある場合 |
| 組織内設置／自己運用 | データ配置や構成を直接管理しやすい | 24時間監視、更新、バックアップ、冗長化、災害対策まで組織が負う | 明確な要件と十分な運用体制がある場合 |

「外部クラウドだから危険」「組織内サーバーだから安全」と単純には判断できません。情報の重要度、利用人数、必要な稼働率、運用能力、費用、契約条件を比較して決めます。

### 5.3 基盤選定時に確認する項目

- 組織名義で契約・支払・管理できるか
- 国内又は組織が認める地域にデータを保存できるか
- 事業者の安全管理措置、第三者認証、事故時の連絡条件を確認できるか
- 再委託先とデータ処理地域を把握できるか
- データの暗号化、アクセス制御、監査ログを利用できるか
- バックアップの対象、頻度、保存期間、復旧時間を確認できるか
- Storage上の画像・ファイルも含めて復旧できるか
- 障害情報、稼働率、サポート窓口、対応時間を確認できるか
- 利用増加時の料金と上限を予測できるか
- 契約終了時にデータを取り出し、確実に削除できるか
- 特定事業者に依存しすぎないための移行手段があるか

## 6. サーバー運用のルール

正式運用の前に、少なくとも次のルールを文書化します。

### 6.1 アカウントと権限

- 管理者、開発者、教員、生徒、問い合わせ担当者ができることを分ける
- 管理者権限を必要最小限の人数に限定する
- 管理者には多要素認証を必須にする
- 共有アカウントを避け、操作した人を特定できるようにする
- 教員の異動、退職、生徒の転出・卒業時に、権限停止とデータ処理を行う
- 管理者権限を定期的に棚卸しする
- 強い権限を持つ鍵やパスワードをソースコード、メール、共有文書へ記載しない

### 6.2 監視と障害対応

- サービス停止、ログイン失敗の急増、保存失敗、容量超過を監視する
- 障害の重大度、連絡先、初動、利用者への告知方法を決める
- 授業中に停止した場合の代替手段を用意する
- 「何分以内に気付き、何時間以内に暫定復旧を目指すか」を定める
- 事故対応後は、原因、影響範囲、再発防止を記録する

### 6.3 バックアップと復旧

- データベースだけでなく、ボードや画像を保存するファイル領域も対象にする
- 復旧可能な時点と許容できるデータ損失量を決める
- バックアップを取得するだけでなく、定期的に復元試験を行う
- バックアップにも本体と同じアクセス制限と保存期限を設定する

### 6.4 更新と変更管理

- 開発環境、検証環境、本番環境を分離する
- 変更内容を別の担当者がレビューする
- 変更前に自動テストと実端末による受入試験を行う
- データベースと画面を同時に変更する場合の順序を決める
- リリース日時、担当者、変更内容、確認結果を記録する
- 問題時に公開停止又は前版へ戻せる手順を用意する
- OS、ライブラリ、クラウドサービスの変更情報と脆弱性情報を継続確認する

### 6.5 ログ

- ログイン、管理操作、設定変更、データ削除、エラーなど、必要な記録を定める
- ログそのものに個人情報やパスワードを過剰に残さない
- 誰がログを閲覧できるか、何日保存するかを決める
- 不正利用や事故の調査に必要な期間とのバランスを取る

### 6.6 問い合わせと日常業務

- 利用申請、クラス作成、アカウント発行、パスワード再設定の手順を定める
- 問い合わせ窓口と対応時間を明示する
- 年度替わりのクラス、アカウント、保存データの処理を定例化する
- 操作マニュアルとよくある質問を更新する責任者を決める

## 7. 個人情報・授業データの取扱いルール

### 7.1 現在のアプリで扱い得る情報

| 情報 | 例 | 現在の主な扱い | 特に考えること |
| --- | --- | --- | --- |
| 教員アカウント | メールアドレス、表示名、認証情報 | 認証・プロフィールとして管理 | 組織IDとの連携、異動・退職時の停止 |
| 生徒アカウント | クラスコード、生徒ログインID、表示名、認証情報 | 認証・クラス名簿として管理 | 実名が必要か、最小限にできるか |
| クラス情報 | クラス名、担当教員、所属関係 | データベースに保存 | 年度更新、クラス終了時の削除 |
| ボードデータ | 手書き、テキスト、図形、挿入画像 | ファイルとして保存可能 | 学習記録としての保存期間、第三者情報の混入 |
| ノート・画面画像 | ノート写真、画面プレビュー、教員の添削 | 主に授業中の通信対象。保存ボードに含まれる場合は保存され得る | 氏名、顔、他アプリ、通知、健康情報等の映り込み |
| チャット・在席・操作情報 | メッセージ、接続状態、利用モード | 現在のコードでは主に授業中のリアルタイム通信 | 保存の要否、監視と受け取られない説明、技術ログの有無 |
| 管理・技術ログ | ログイン、削除、エラー、接続情報 | 提供基盤に記録される場合がある | 調査目的、保存期間、閲覧者、本人への説明 |

パスワードそのものをアプリの名簿テーブルへ平文保存する設計ではありませんが、認証基盤が認証情報を管理します。また、表示名を仮名にしても、クラス所属や作品と結び付けば個人を識別できる場合があります。

### 7.2 組織として決めるべき項目

1. **利用目的**
   - 授業中の学習支援、教材配布、共同編集など、目的を具体的に限定します。
   - 目的外の評価、行動監視、二次利用を行う場合は、別途妥当性と説明を検討します。

2. **収集する情報の最小化**
   - 実名、生年月日、メールアドレスなどが本当に必要かを項目ごとに判断します。
   - 生徒IDや表示名は、既存の校務IDと連携するのか、このアプリ専用の仮名にするのかを決めます。

3. **閲覧・操作できる人**
   - 担任、教科担当、管理者、支援員、開発・保守担当の閲覧範囲を決めます。
   - 保守担当が実データを見る必要がある場合は、目的、期間、記録、秘密保持を定めます。

4. **保存期間と削除**
   - 授業終了、学期末、年度末、卒業・転出、利用停止時に何を削除するかを定めます。
   - 本体だけでなく、ファイル、バックアップ、ログ、テスト用コピーも対象にします。

5. **本人・保護者等への説明**
   - 何を、なぜ、どこに、いつまで保存し、誰が見られるかを平易に説明します。
   - 同意が必要か、通知・公表で足りるかは、組織の法務・個人情報保護担当が制度と利用目的に応じて判断します。

6. **画面確認・撮影機能の扱い**
   - 教員がいつ画面を確認できるか、利用者にどのように表示するかを明確にします。
   - ノート撮影や画面共有では、顔、氏名、他のアプリ、通知などが映らないように利用上の注意を示します。

7. **外部委託・クラウド利用**
   - 委託先の安全管理措置、再委託、保存地域、監査、事故連絡、契約終了時の返却・削除を確認します。
   - 契約後も、必要に応じて取扱状況を確認します。

8. **開示・訂正・削除等への対応**
   - 利用者から自分の情報について問い合わせがあった場合の窓口と手順を定めます。

9. **漏えい等の事故対応**
   - 誰が事実確認し、サービスを止め、組織内へ報告し、本人や監督機関への対応を判断するかを決めます。

### 7.3 個人開発環境での実データ利用について

組織の正式利用へ進む場合、個人名義のクラウドや個人管理のアカウントを本番データの保管場所にしないことが原則です。少なくとも、組織の承認が終わるまでは架空データだけを使用します。

現在の個人環境に実データが存在する場合は、自己判断で移動・複製・削除せず、組織の情報管理責任者と次を行います。

- 何が、どこに、どれだけ保存されているかを記録する
- 利用目的と保存根拠を確認する
- 組織環境へ移すデータと削除するデータを決定する
- 移行中の暗号化、アクセス権、作業担当者、作業記録を定める
- 個人環境からの削除と、削除後の確認方法を定める
- 必要な報告・説明があるかを個人情報保護担当と判断する

## 8. 専門家による技術支援

### 8.1 必要な専門性

| 専門分野 | 主な役割 | このアプリで必要な理由 |
| --- | --- | --- |
| システム設計 | 要件を基に全体構成と移行方針を決める | 認証、保存、通信、管理機能が密接に連携しているため |
| バックエンド／データベース | データ構造、権限、管理API、移行を設計する | クラス・所有者単位の細かなアクセス制御が必要なため |
| クラウド／インフラ運用 | 環境構築、監視、バックアップ、復旧、費用管理 | 稼働後も継続的な運用が必要なため |
| セキュリティ | 脅威分析、設計レビュー、診断、事故対応を支援する | 生徒情報、画像、認証、リアルタイム通信を扱うため |
| 個人情報保護・法務 | 利用目的、規程、委託契約、本人説明を確認する | 技術だけでは適法性や組織規程への適合を判断できないため |
| 品質保証／テスト | 実端末、複数利用者、負荷、障害時の動作を検証する | 一人の端末で動くことと、授業全体で安定することは別だから |
| アクセシビリティ／利用設計 | 読みやすさ、操作しやすさ、支援技術対応を確認する | 多様な利用者と端末が授業で使用するため |

全てを常勤の専任者として置く必要はありません。組織内担当者、既存の情報部門、外部専門家を組み合わせることは可能です。ただし、**助言を受ける人だけでなく、最終的に決定し、運用を引き受ける組織内責任者**が必要です。

### 8.2 専門家へ依頼したい具体的な確認

- 現行コードとデータ構造の技術監査
- 認証、権限、ファイルアクセス、リアルタイム通信の設計レビュー
- 管理者用秘密情報の保管方法の確認
- 脆弱性診断と修正後の再診断
- バックアップ対象と復旧試験の設計
- Supabaseから候補基盤への移行可能性と工数見積り
- 同時接続数、画像通信量、保存容量、応答時間の負荷試験
- iPad、Chromebook、Windows等の実利用端末での受入試験
- 障害、通信切断、ブラウザ更新、端末強制終了時のデータ保護確認
- 開発者以外が保守できる文書と引継ぎの整備

## 9. Supabaseから別の基盤へ移行する場合

### 9.1 移行対象

| 現在Supabaseが担うもの | 移行先で必要な代替 | 主な移行作業 |
| --- | --- | --- |
| Auth | 組織ID基盤又は新しい認証サービス | 教員・生徒の本人確認、パスワード再設定、セッション管理 |
| Database／RLS | DBとサーバー側の認可 | テーブル移行、教員・生徒・クラス・所有者ごとの権限再実装 |
| Storage | 非公開オブジェクトストレージ又はファイル基盤 | ボードJSON・画像の移行、アクセス制御、完全性確認 |
| Realtime | WebSocket等の双方向通信基盤 | 在席、チャット、画面確認、共同編集、再接続処理の再実装 |
| Edge Functions | 組織サーバー上の管理API | 生徒作成・削除、パスワード再設定、一斉配布等の再実装 |
| Logs／Usage | 監視・ログ基盤 | エラー監視、監査記録、容量・費用アラートの構築 |

現在のフロントエンドは `public/js/supabase-api.js` を通じてこれらの機能を利用しています。ホワイトボード画面や描画機能を全て作り直す必要はない可能性がありますが、移行先に合わせた通信部分と管理処理の改修は必要です。

### 9.2 特に注意する点

- **認証情報は単純コピーできない場合がある**
  - パスワードを復号して移すことは通常できません。新基盤でのパスワード再設定、アカウント再発行、組織ID連携などを検討します。
- **アクセス制御を同等以上に再現する必要がある**
  - 現在は教員、生徒、所属クラス、ファイル所有者、通信先ごとに制限しています。移行時に一時的に全員が閲覧できる状態を作ってはいけません。
- **DBのバックアップだけではファイルが戻らない場合がある**
  - ボードや画像の実体と、DB上のファイル台帳を一組として移行・検証します。
- **画面とサーバーを同時に切り替える必要がある部分がある**
  - リアルタイム通信の経路や権限ルールは、片方だけを先に変更すると接続不能になる場合があります。
- **データ移行とサービス切替を分けて計画する**
  - 予行演習、件数照合、ファイル照合、切替時間、旧環境への書込み停止、切戻し条件を定めます。
- **移行先から再び移れる設計にする**
  - データ形式、エクスポート手順、構成情報を文書化し、事業者変更や契約終了に備えます。

### 9.3 Supabaseを継続利用する場合でも必要なこと

Supabaseを組織名義で継続する選択肢もあり得ます。ただし、サービスを利用するだけで安全性や運用責任が自動的に解決するわけではありません。

- 組織名義の契約、請求、管理者アカウントに移す
- データ保存地域、契約条件、再委託、サポート、事故通知を確認する
- 無料枠を本番前提にせず、必要なバックアップ、監視、容量、復旧機能を選ぶ
- Supabaseの仕様変更・廃止予定を継続確認する
- RLS、Storage、Realtime、Edge Functionsの設定を定期監査する
- 本番、検証、開発を別プロジェクトに分ける

## 10. 個人開発から組織開発へ移すための手順

### 段階0：正式検討の開始

**行うこと**

- 事業責任者、サービス管理責任者、情報管理責任者を決める
- 利用目的、対象者、利用場面、想定人数を定める
- 実在する利用者データを新たに個人環境へ入れない
- 現在のコード、クラウド、ドメイン、秘密情報、データ、素材の一覧を作る

**次へ進む条件**

- 誰が責任を持つか、検討中にどのデータを使ってよいかが文書化されている

### 段階1：要件・ルール・権利の整理

**行うこと**

- 必要機能と不要機能を整理する
- 個人情報、保存期間、削除、画面確認のルールを決める
- コード、画像、アイコン、フォント、ライブラリの権利を確認する
- 必要な可用性、端末、ブラウザ、同時利用人数を決める
- 概算費用と調達方法を確認する

**次へ進む条件**

- 個人情報保護、情報セキュリティ、法務、現場代表の確認が得られている

### 段階2：基盤選定と組織所有への移行

**行うこと**

- 候補基盤を同じ要件で比較する
- 組織名義のGit、クラウド、ドメイン、監視、連絡先を用意する
- 個人アカウントへの依存をなくし、複数の組織管理者を置く
- 開発・検証・本番環境を分ける
- 秘密鍵、招待コード、管理者パスワードを再発行する

**次へ進む条件**

- 個人が不在でも、組織が契約・停止・復旧・権限変更を行える

### 段階3：組織内ステージング

**行うこと**

- 架空データだけで全機能を確認する
- 自動テスト、権限テスト、脆弱性診断、負荷試験、復旧試験を行う
- 教員1名・複数生徒・複数端末で認証済みの一連の動作を確認する
- 操作マニュアル、問い合わせ、障害連絡を試行する

**次へ進む条件**

- 重大な脆弱性が解消され、バックアップからの復旧と緊急停止が確認できている

### 段階4：限定実証

**行うこと**

- 対象、期間、機能、データを限定して実施する
- 利用者へ取扱いと問い合わせ先を説明する
- 通信量、保存量、障害、問い合わせ、教育上の効果と負担を記録する
- 実証終了後のデータ削除又は継続保管を確認する

**次へ進む条件**

- 技術面だけでなく、教育上の有用性、現場負担、費用、個人情報保護を含めて正式導入を判断できる

### 段階5：正式運用

**行うこと**

- 利用申請、アカウント管理、監視、更新、事故対応を定常業務にする
- 定期的な権限棚卸し、復旧訓練、脆弱性確認、規程見直しを行う
- 利用状況と教育上の効果を評価し、継続・改善・停止を判断する

## 12. 追加で考えるべきこと

### 12.1 このアプリを何のために使うのか

- 授業支援に限定するのか、学習評価にも用いるのか
- どの機能が教育上不可欠で、どの機能はなくてもよいか
- 画面確認機能が必要な場面と、利用者への表示方法
- 保存されたボードを成績資料や指導記録として扱うのか

用途が変われば、必要な説明、保存期間、アクセス権、システム要件も変わります。

### 12.2 対象規模と性能

- 同時に利用する教員数、生徒数、クラス数
- 1授業の長さと1日の授業回数
- 画像、ノート、ボードの平均容量と保存期間
- 学校回線、家庭回線、端末性能の差
- 災害時や通信障害時にどこまで利用を継続するか

現在の既存資料にある「教員1名・生徒3名以内・45分以内」は、無料枠を想定した初期テストの目安であり、組織導入時の性能保証ではありません。正式な対象規模で負荷試験が必要です。

### 12.3 端末・操作性・アクセシビリティ

- 対応するiPad、Chromebook、Windows、ブラウザの範囲
- タッチ、ペン、キーボードのみでの操作
- 色覚、視力、運動、認知等の多様性への配慮
- 画面サイズとネットワーク帯域が小さい環境での利用
- カメラ・画面共有権限を拒否した場合の代替操作

### 12.4 知的財産・ライセンス

- 個人が作成したコードを組織が使用・改変・公開できることの確認
- 外部委託先が作成した成果物の権利帰属
- JavaScriptライブラリ、画像、スタンプ、アイコン、フォントの利用条件
- オープンソースとして公開するか、組織内限定にするか
- 利用者が作成したボードや提出画像の権利と利用範囲

### 12.5 費用

- クラウド基本料金、通信量、ファイル容量、バックアップ、ログ
- ドメイン、証明書、監視、メール送信、サポート契約
- 開発、レビュー、診断、保守、問い合わせ、研修
- 端末・ブラウザ試験と予備環境
- 料金上昇や利用者増加に備えた予備費

### 12.6 終了時の計画

- サービス停止を誰が決め、どのように周知するか
- 利用者データを返却、出力又は削除する方法
- バックアップと外部事業者側のデータをいつ削除するか
- ソースコード、設計、運用記録をどこへ保管するか
- 後継サービスへの移行形式をどうするか

サービス開始時に終了方法まで決めておくことで、特定の個人や事業者に依存しにくくなります。

- [ ] 想定人数と画像利用を含む負荷試験を完了している

- [ ] サービス終了時のデータ出力・削除・移行方法が決まっている

## 15. 推奨する当面の進め方

当面は、次の順で進めることを推奨します。

1. **組織内の責任者と検討チームを決める。**
2. **現行環境にあるコード、データ、アカウント、秘密情報、素材を棚卸しする。**
3. **実在データを使わず、必要機能、利用人数、保存期間、画面確認の取扱いを決める。**
4. **組織の個人情報保護・情報セキュリティ・法務担当の確認を受ける。**
5. **組織の既存基盤、組織名義のマネージドサービス、個別構築を同じ要件で比較する。**
6. **専門家に現行コードの設計・セキュリティ・移行可能性を評価してもらう。**
7. **組織名義の検証環境を作り、架空データで複数端末試験と復旧試験を行う。**
8. **条件を限定した実証を経てから、正式運用を判断する。**

最初から「どのサーバー製品を買うか」を決めるより、先に利用目的、扱う情報、必要規模、運用責任を定める方が、過不足のない基盤と費用を選びやすくなります。
